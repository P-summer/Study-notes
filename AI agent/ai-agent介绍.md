# 📝 AI Agent 面试核心笔记（贴合个人项目版）
## 🔍 项目核心速览（快速回忆）
### 项目整体架构
- **前端**：Vue3 + TypeScript + Element Plus + Pinia + Vue Router，轻量化交互层，聚焦对话体验与会话管理
- **后端**：Node.js（v18+）+ Express + LangChain/LangGraph，核心实现Agent逻辑
- **数据层**：Chroma 向量数据库（本地部署），支撑RAG与长期记忆
- **部署架构**：Nginx反向代理 → Node.js服务（3000端口）→ LLM/Chroma，阿里云ECS（Linux）部署
- **核心能力**：多模型兼容、ReAct/Planner双执行模式、代码库RAG、长短时记忆、SSE流式输出、会话Token管控

### 核心脚本/命令（项目实操）
| 命令                  | 作用                                  |
|-----------------------|---------------------------------------|
| `pnpm dev`（前端/后端） | 启动开发环境（热重载）|
| `pnpm start`（后端）| 启动生产环境                          |
| `pnpm index-codebase`（后端） | 代码库切片→向量化→存入Chroma（RAG初始化） |
| `pnpm clear-old-chroma`（后端） | 清理Chroma过期数据/无效集合           |

## 🧠 一、项目相关问题（核心必记，贴合落地）
### ❓1. 介绍一下你的 AI Agent 项目
**核心回答（结合项目）**：
我独立完成了一套AI Agent全栈系统，前端基于Vue3+TypeScript+Element Plus构建交互层，后端基于Node.js+Express开发，核心用LangChain+LangGraph搭建Agent执行引擎，搭配Chroma向量数据库实现RAG与长期记忆。
核心落地能力：
- 多模型兼容：封装LLM Adapter适配DeepSeek/豆包等模型，统一OpenAI API格式，上层无感切换
- 双执行模式：支持ReAct（动态推理）和Planner（先规划后执行），适配不同任务场景
- 代码库RAG：将后端代码切片向量化存入Chroma，可检索代码片段辅助生成答案
- 记忆体系：短期记忆维护会话上下文，长期记忆基于Chroma跨会话存储；SSE流式输出提升交互体验
- 资源管控：基于Token计数限制会话长度，避免资源过度消耗

### ❓2. 你的 Agent 是怎么实现的？（双模式细节）
**核心回答（结合项目）**：
基于LangGraph实现状态机式的Agent执行流程，核心落地两种模式：
1. **ReAct模式**：
   - 流程：Thought（LLM推理下一步行动）→ Action（调用工具/LLM）→ Observation（获取执行结果）→ 循环至任务完成
   - 项目落地：用于动态、不确定性的简单任务（如实时信息查询），通过LangChain的Tool调用能力封装时间工具、Google SERPER工具等
2. **Planner模式**：
   - 流程：先让LLM拆解复杂任务为结构化子步骤（如“代码检索→逻辑分析→答案生成”），再按步骤调用对应工具/LLM执行
   - 项目落地：用于代码库检索+答疑这类复杂任务，先规划步骤再执行，减少无效操作
3. 核心差异（项目体感）：ReAct灵活但易重复调用工具，Planner稳定但适配性弱，项目中可根据任务类型自动/手动切换

### ❓3. 你是怎么做 RAG 的？（代码库RAG为核心亮点）
**核心回答（结合项目）**：
项目聚焦“代码库RAG”落地，完整流程：
1. 文档切片：通过脚本遍历后端代码文件，按「文件/函数/类」拆分片段（而非纯文本切割），保证代码语义完整性
2. 向量化：调用嵌入模型将代码片段转为embedding向量
3. 存储：存入Chroma向量库，为每个片段添加metadata（文件路径、类型、修改时间）
4. 检索：用户提问时，将问题向量化后在Chroma中做相似度检索，返回TopK相关代码片段
5. 增强生成：将检索结果拼接至Prompt，传给LLM生成答案
项目优化点：控制chunk大小（避免过长/过短）、添加metadata提升检索精度、限制TopK（减少冗余）

### ❓4. 为什么选择 Chroma？（而非其他向量库）
**核心回答（结合项目）**：
项目选择Chroma核心是贴合“本地开发+轻量化落地”需求：
- 轻量易部署：本地即可运行，无需复杂集群配置，适配个人项目部署（阿里云ECS低配服务器也能跑）
- 集成友好：与LangChain无缝对接，无需额外封装适配层
- 功能适配：支持metadata过滤（代码库RAG需按文件路径/类型筛选）、相似度检索，满足长短时记忆存储需求
- 操作便捷：自定义脚本可快速清理/初始化集合，适配代码库RAG的频繁更新场景

### ❓5. 多模型是怎么接入的？（项目封装细节）
**核心回答（结合项目）**：
封装统一的LLM Adapter层，屏蔽不同模型的接口差异：
1. 抽象核心方法：定义`chat`（同步对话）、`streamChat`（流式对话）、`embedding`（向量化）三个核心方法
2. 适配层实现：对DeepSeek/豆包等模型，分别实现上述方法，统一输出格式为OpenAI API规范
3. 上层调用：Agent/ RAG模块直接调用Adapter层，无需关心底层模型，通过环境变量/前端选择即可切换模型
项目价值：降低多模型切换成本，后续新增智谱/讯飞等模型仅需新增适配层实现

### ❓6. 流式输出是怎么实现的？（前后端联动）
**核心回答（结合项目）**：
基于SSE（Server-Sent Events）实现，前后端联动落地：
- 后端：调用LLM的streaming API，每获取一段生成内容，通过Express的SSE响应流实时返回（Content-Type: text/event-stream）
- 前端：封装Axios监听SSE流，逐段接收内容并拼接渲染（用marked解析Markdown），实现类似ChatGPT的实时输出效果
对比WebSocket：SSE更轻量，无需双向通信，适配AI对话“单向流式输出”场景，项目中实现成本更低

### ❓7. 你项目中最大的难点是什么？（问题+落地解决方案）
**核心回答（结合项目）**：
最大难点是Agent执行的“稳定性控制”，具体问题+解决方案：
1. 问题：LLM不稳定导致重复调用工具（如多次检索同一代码片段）
   解决：限制Agent最大执行步数（如最多8步），检测重复的Tool调用行为，触发则终止循环
2. 问题：上下文过长导致Token消耗过高、响应变慢
   解决：基于tiktoken计算Token长度，超过阈值时压缩历史对话（保留核心信息），同时限制RAG返回的TopK数量
3. 问题：Planner模式步骤拆解不合理
   解决：优化Prompt，约束步骤拆解的格式（如JSON数组），并添加“步骤校验”逻辑，不合理则重新生成

### ❓8. 你的 RAG 是如何优化的？（落地优化点）
**核心回答（结合项目）**：
针对“代码库RAG”做了专项优化：
1. 切片优化：放弃纯文本按长度切片，改为基于代码语法（函数/类/文件）拆分，保证代码语义完整
2. 检索精度：为每个代码片段添加metadata（文件路径、代码类型），检索时可过滤无关片段
3. 性能优化：控制chunk大小（单片段≤500字符），避免向量计算耗时；限制返回Top3~Top5，减少冗余
4. 数据新鲜度：提供脚本`clear-old-chroma`定期清理过期代码向量，保证检索结果为最新代码

## 🧠 二、AI Agent 高频基础问题（精准记忆）
### ❓9. 什么是 AI Agent？
**核心回答**：
具备“推理+执行+记忆”能力的自主系统，核心四要素：
- LLM：核心决策层，负责推理、规划、调用工具
- Tools：扩展执行能力（如我的项目中的时间工具、代码检索工具）
- Memory：长短时记忆（项目中Chroma+上下文缓存）
- Loop：执行循环（ReAct/Planner，项目中基于LangGraph实现）

### ❓10. ReAct 是什么？
**核心回答**：
ReAct是Agent的核心执行范式，全称Reasoning（推理）+ Acting（行动），核心流程：
Thought（推理下一步做什么）→ Action（调用工具/生成内容）→ Observation（观察执行结果）→ 重复至任务完成
项目中用于动态、不确定性任务（如实时信息查询）。

### ❓11. Planner 和 ReAct 区别？（项目体感）
| 维度       | ReAct                  | Planner                |
|------------|------------------------|------------------------|
| 核心逻辑   | 边做边想（动态推理）| 先想后做（先规划再执行） |
| 项目适配   | 简单/动态任务（如时间查询） | 复杂任务（如代码库RAG答疑） |
| 优缺点     | 灵活但易重复/不稳定    | 稳定但适配性弱          |

### ❓12. 什么是 RAG？
**核心回答**：
检索增强生成（Retrieval-Augmented Generation），核心逻辑：生成答案前，先从外部知识库（如我的项目中的代码库向量库）检索相关信息，再结合LLM生成答案，解决模型幻觉、知识过时问题。
项目落地：代码库RAG（非修改模型参数，仅补充外部知识）。

### ❓13. RAG 和 Fine-tune 区别？（结合项目场景）
| 维度       | RAG（项目用）| Fine-tune              |
|------------|------------------------|------------------------|
| 核心逻辑   | 不修改模型，补充外部知识 | 修改模型参数，灌输知识 |
| 项目适配   | 代码库知识频繁更新（低成本） | 知识固定、高成本场景（未落地） |
| 落地成本   | 低（仅维护向量库）| 高（数据标注+训练+部署） |
| 时效性     | 实时更新（脚本重新向量化） | 慢（需重新训练）|

### ❓14. embedding 是什么？（项目落地）
**核心回答**：
将文本/代码转换为高维数值向量（embedding），向量的距离代表语义相似度；
项目中：用嵌入模型将代码片段/用户问题转为向量，存入Chroma，通过向量相似度检索相关代码。

### ❓15. 向量数据库作用？（结合项目）
- 存储：高效存储embedding向量（项目中存代码/会话记忆向量）
- 检索：快速做语义相似度检索（核心）
- 扩展：支持metadata过滤、跨会话查询（项目中代码库RAG的核心依赖）

### ❓16. Prompt Engineering 是什么？（项目实操）
**核心回答**：
通过设计Prompt控制LLM行为，项目中主要落地：
- 角色指定：让LLM扮演“代码答疑助手”
- 格式约束：Planner模式要求LLM输出JSON格式的步骤列表
- 推理控制：约束ReAct模式的思考逻辑，减少无效操作

### ❓17. Function Calling 是什么？（项目落地）
**核心回答**：
让LLM不再仅返回文本，而是调用结构化的函数/工具；
项目中：基于LangChain的Tool封装能力，实现时间工具、代码检索工具的结构化调用，LLM根据推理结果选择工具并传入参数，后端执行后返回结果。

## 🧠 三、进阶问题（拉开差距，结合项目）
### ❓18. AI Agent 最大挑战是什么？（项目体感）
**核心回答**：
本质是让“生成式LLM”变成“可控的工程化系统”，核心挑战：
- 不确定性控制：LLM可能生成错误的工具调用指令（项目中通过Prompt约束+步骤限制解决）
- 上下文管理：长会话Token超限、上下文冗余（项目中通过Token计数+历史压缩解决）
- 工具调用可靠性：重复调用、参数错误（项目中添加工具调用校验+重复检测）

### ❓19. 如何减少 hallucination（幻觉）？（项目落地）
**核心回答**：
项目中多维度规避：
1. 核心手段：代码库RAG，强制LLM基于检索到的代码片段生成答案
2. 约束手段：Prompt中添加“无相关信息时明确说明，不编造内容”的系统指令
3. 精度手段：RAG检索限制TopK，仅返回高相似度代码片段
4. 格式手段：约束输出格式（如代码片段标注来源文件），便于校验
  
**也就是**：
1. 不让模型瞎想：Prompt 强约束
2. 不让模型瞎编：RAG 给原文依据
3. 不让模型瞎猜：不确定就调用工具
4. 不让模型瞎说：格式 + 流程 + 校验限制

### ❓20. 如何控制 token 成本？（项目实操）
**核心回答**：
项目中从多环节管控：
- 上下文：基于tiktoken计算Token长度，超限则压缩历史对话（保留核心问题/结果）
- RAG：限制检索返回Top3~Top5，减少拼接至Prompt的内容长度
- Prompt：精简系统指令，仅保留核心约束（如角色+格式）
- 执行流程：限制Agent最大执行步数（如8步），减少不必要的LLM调用

### ❓21. 为什么用 LangChain / LangGraph？（项目选型）
| 工具       | 选型原因（项目落地）|
|------------|------------------------|
| LangChain  | 封装了LLM/工具/向量库的适配层，减少重复开发（如多模型适配、Tool调用） |
| LangGraph  | 基于状态机实现复杂流程控制，适配Agent的循环执行逻辑（ReAct/Planner），可控性更强 |

### ❓22. LangGraph 有什么优势？（项目体感）
- 流程可视化：可定义节点（推理/工具调用）和边（状态转移），清晰管控Agent执行路径
- 状态管理：统一维护会话状态（如当前步骤、上下文、工具调用结果），避免状态混乱
- 扩展灵活：新增执行模式/工具仅需新增节点，无需重构整体逻辑（项目中新增Planner模式仅扩展规划节点）

### ❓23. Memory 是怎么设计的？（项目核心）
**核心回答**：
项目落地“长短时记忆分离”架构：
- 短期记忆：基于内存缓存维护当前会话上下文，随会话关闭销毁，保证多轮对话连贯性
- 长期记忆：将会话关键信息/代码片段转为向量存入Chroma，支持跨会话检索（如历史代码答疑记录）
- 交互：前端会话管理模块可切换会话，后端根据会话ID加载对应长短时记忆

### ❓24. Agent 如何避免死循环？（项目解决方案）
**核心回答**：
项目中三重防护：
1. 步数限制：设置Agent最大执行步数（如8步），超过则终止循环并返回当前结果
2. 重复检测：记录每轮调用的工具/参数，若连续2次调用相同工具+相同参数，判定为重复，终止循环
3. 终止条件：明确任务完成的判定Prompt（如“答案生成完成”“检索结果为空”），LLM推理满足条件则终止

## 🎯 面试答题技巧（必看）
1. **结构化回答**：先讲核心结论，再分点补充（如“我做了XX项目，核心能力有3点：1...2...3...”）
2. **结合项目实例**：每个问题尽量带项目实操细节（如“我在项目中通过XX脚本实现了XX功能”）
3. **避空泛，讲落地**：少讲“概念”，多讲“我做了什么/怎么解决的”
4. **主动引导**：回答时可自然带出项目亮点（如讲RAG时主动提“我做的是代码库RAG，而非普通文本RAG”）
